Found **3 P1 correctness bugs, 2 P2 mismatches, and 2 P3 test gaps**.

1. **P1 — Dependency memoization ignores observable timestamp changes.**  
   [pkg/health/rollup.go:128](../../../../pkg/health/rollup.go#L128), [rollup.go:257](../../../../pkg/health/rollup.go#L257)  
   A memo hit restamps `CheckResult.CollectedAt` but returns the cached output fingerprint; `outputPrint` explicitly excludes that timestamp. A downstream check declaring `Checks: ["earlier"]` may legally copy `Output("earlier").Result.CollectedAt` into its finding detail. After time advances, the earlier result changes while the dependent remains memoized indefinitely. The uncached engine produces different findings. **R18 is too broad:** treating timestamps specially for response restamping does not make them unobservable to dependent checks.

2. **P1 — Vanished cursor anchors can skip unchanged findings.**  
   [pkg/diagnose/index.go:263](../../../../pkg/diagnose/index.go#L263)  
   When an anchor disappears, paging resumes from its old numeric position rather than its ordering tuple. Example: read `[A,B]` from `[A,B,C,D,E]`; then A and B resolve. The cursor retains position 1, so the next page over `[C,D,E]` starts at D and silently skips C. Phase 3 §13.1 promises Phase 2 keyset semantics, including insertion-point recovery for vanished anchors. The current cursor lacks enough information to provide that behavior.

3. **P1 — Restricted finding IDs disclose hidden condition information.**  
   [pkg/health/checks.go:219](../../../../pkg/health/checks.go#L219), [pkg/api/findings.go:150](../../../../pkg/api/findings.go#L150)  
   KGWUI-002 hashes the condition type into its ID, then exposes that ID on restricted rows. A caller already knows install, code, resource identity, and the public hash algorithm. For a hidden Gateway, computing candidates with `["self","Accepted"]` and `["self","Programmed"]` identifies which hidden condition failed. Hashing low-entropy values does not conceal them. **R24 contradicts §14 rule 11**; D-024’s exception for ancestor names does not authorize revealing hidden condition types. This needs an explicit resolution of the identity/authentication design conflict.

4. **P2 — Breadcrumbs treat syntactically valid URL entries as resolved objects.**  
   [web/packages/shell/src/shell/Breadcrumbs.tsx:175](../../../../web/packages/shell/src/shell/Breadcrumbs.tsx#L175)  
   If a crumb is absent from the page’s known refs, `resolve` constructs a link and displays its URL-provided name. Thus a deleted object remains clickable, and a hidden object shows its name whenever the current page does not happen to hold its `LinkedRef`. §17.6 requires unresolved entries to be plain text and hidden entries to use the restricted label. **R31 weakens both requirements:** the destination returning “not in scope” does not validate the breadcrumb.

5. **P2 — Core detail pages never receive the required wide-screen second column.**  
   [web/packages/shell/src/pages/explore/detailParts.tsx:175](../../../../web/packages/shell/src/pages/explore/detailParts.tsx#L175), [web/e2e/navigation.spec.ts:216](../../../../web/e2e/navigation.spec.ts#L216)  
   Core detail pages supply no side content, so they remain single-column at 1600 and 3008 px. The browser tests explicitly require that behavior. D-035, §17.6, Task 28, and the brief require conditions/findings/related objects beside the structure at those widths. **R30 removes the requested behavior rather than adjusting its presentation.** The four-width checks therefore pass while asserting the opposite acceptance condition.

6. **P3 — The declared-input guard can hide undeclared reads behind persisted state.**  
   [internal/testutil/healthtest/inputs.go:150](../../../../internal/testutil/healthtest/inputs.go#L150)  
   Baseline and perturbed evaluations share the same mutable `States`, contrary to Task 17’s fresh-Store requirement. A check that reads an undeclared input once, stores it, and subsequently returns that stored value passes this guard. Conversely, legitimate state transitions can fail it. Comparisons need equivalent starting state for each branch, with engine-generated identity/`since` handled separately. This matters as 3.2–3.4 introduce more stateful checks.

7. **P3 — The vanished-anchor test asserts the implementation’s offset mechanism.**  
   [pkg/api/findings_test.go:438](../../../../pkg/api/findings_test.go#L438)  
   The test pins the exact cursor JSON containing `"v":1` and removes only B, a case where offset fallback happens to work. It does not preserve fixed ordering keys while removing multiple preceding findings or inserting rows before the vanished anchor. Consequently it endorses the mechanism responsible for finding 2 instead of verifying the promised continuation behavior.

I did not edit files or run tests. The supplied passing results do not cover these counterexamples.
