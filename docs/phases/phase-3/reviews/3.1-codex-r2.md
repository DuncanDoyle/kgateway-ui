**New issues, ranked**

1. **P1 — Cross-install cursor replay exposes hidden timestamp comparisons.**  
   [pkg/diagnose/index.go:288](../../../../pkg/diagnose/index.go#L288), [index.go:342](../../../../pkg/diagnose/index.go#L342), [index.go:389](../../../../pkg/diagnose/index.go#L389)  
   The sealed payload has no install identifier, the associated data is only `"findings"`, and the encryption key is shared process-wide. A cursor issued for a restricted finding in install A is accepted against install B with the same sort/direction. For `since`, B’s returned rows disclose how their known timestamps compare with A’s hidden timestamp. A caller able to vary visible findings in B gains a comparison oracle. This disclosure is newly introduced by carrying hidden timestamps in reusable cursors; the old offset cursor contained no such timestamp. Authenticate the install identity and reject cross-install replay.

2. **P1 — Cursor timestamps can disagree with the actual sort order.**  
   [pkg/diagnose/index.go:232](../../../../pkg/diagnose/index.go#L232), [index.go:241](../../../../pkg/diagnose/index.go#L241)  
   Orders use `time.Time.Compare`, while cursor comparisons use `UnixNano()`. Go documents that conversion as undefined before 1678 or after 2262; Kubernetes timestamp decoding accepts RFC3339 dates outside that interval, and `since()` does not reject them. For ascending timestamps `[2026, 2300, 2301]`, the latter values wrap negative. Continuing after 2026 can binary-search past both remaining rows, even with no recompute or deletion. This affects `since` and timestamp tie-breaking in rank/code. Serialize seconds plus nanoseconds, or another representation preserving the complete supported time order.

3. **P1 — Valid collapsed trails exceed the endpoint’s six-ref limit.**  
   [web/packages/shell/src/shell/Breadcrumbs.tsx:342](../../../../web/packages/shell/src/shell/Breadcrumbs.tsx#L342), [pkg/api/refs.go:43](../../../../pkg/api/refs.go#L43)  
   `TRAIL_MAX` limits displayed crumbs; older entries remain in the ellipsis menu. The shell sends **all** earlier objects in one lookup, but `/refs` rejects more than six. A valid trail containing seven distinct earlier objects therefore returns 400. Unheld visible objects then become restricted labels and lose their links, including crumbs outside the menu. Batch requests within the bound or define a bound covering the retained trail.

4. **P2 — A transient network failure permanently mislabels crumbs for that mounted page.**  
   [web/packages/shell/src/api/exploreHooks.ts:123](../../../../web/packages/shell/src/api/exploreHooks.ts#L123), [Breadcrumbs.tsx:351](../../../../web/packages/shell/src/shell/Breadcrumbs.tsx#L351)  
   `apiFetch` represents network failures as status **0**. The new hook retries only statuses ≥500 and disables focus/reconnect revalidation; `Breadcrumbs` treats every status <500 as a final restricted result. A brief connection loss therefore converts authorized crumbs to restricted labels without recovery on reconnect. Retry status 0 and reserve final restricted fallback for terminal responses.

**Additional security checks:** `/refs` delegates to the existing Authorizer-backed linker. Hidden and absent objects both return the submitted identity with `link: "none"`; I found no extra existence distinction in its response. It validates count, components and served kinds, although parsing occurs before those bounds and has no endpoint-specific raw-query cap.

The HMAC-derived nonce does **not** create an immediate GCM break merely by repeating an identical cursor: plaintext and associated data repeat together, the exception described in [RFC 5116 §5.1.1](https://www.rfc-editor.org/rfc/rfc5116#section-5.1.1). It does reveal equality and retains a 96-bit collision bound for distinct plaintexts, with no explicit usage cap or rotation. Keys are process-local, so restart or another replica invalidates cursors. List/sort/direction binding and malformed/tampered-cursor error paths are present; install binding is missing as reported above.
