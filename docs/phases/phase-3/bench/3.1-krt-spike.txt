## What the spike built

View A (attachment) as krt collections, kgateway 2.4 rule set only:
- inputs: MutableCollection of Gateway/ListenerSet resources, MutableCollection of routes, a StaticSingleton
  for the rest of AttachmentInput (namespace labels, settings, controller names, scope);
- derived: resources -> parsed listener states (NewCollection) -> per-parentRef outcome, members and
  per-listener count contributions (NewManyCollection, FetchOne by resource key);
- fed from the same snapshot the engine already reads, by diff against the last fed value per object,
  so only changed objects become krt events (what informer events would deliver);
- each recompute waits for a barrier, then copies the collections into one immutable
  AttachmentResult (sorted as the full recompute sorts) that goes into Published as before.
Checks, views B and C, and everything after the views are unchanged.

Correctness: the krt view A is reflect.DeepEqual to the full recompute at Large and
Large-contradicting, before and after a one-route edit (TestKrtViewAEqual, spike branch).
All unit tests pass on the spike branch, four runs in a row, and pkg/engine under -race.

Per-request consistency needs a hand-built barrier. krt has no flush or settle call, and
every handler gets its own delivery goroutines, so events from different inputs reach a derived
collection in no fixed order. The first barrier (one sentinel through routes and resources together)
raced: golden and visibility tests in pkg/api failed intermittently with a half-updated view A.
The working barrier crosses each input path in turn (globals, resources -> states -> outputs,
routes -> outputs) and waits for each, three round trips per recompute.

## Decision rule (design §16.1), applied

| Criterion                                          | Measured                                                        | Pass |
|----------------------------------------------------|-----------------------------------------------------------------|------|
| Spec-edit stream CPU at least 40 % lower           | 14.2 % vs 10.9 % of one core: 30 % higher                        | fail |
| Retained heap no more than +16 MiB                 | +16.5 to +19.4 MiB over the current engine (4 medians)           | fail |
| Every request reads one immutable published value  | yes, but only through a hand-built three-step barrier           | pass |
| No replace directives                              | 0                                                               | pass |
| Apache-2.0 compatible licences                     | Apache-2.0, MIT, BSD, MPL-2.0                                   | pass |

Verdict: Keep. Keep the immutable full recompute and add per-check memoization (§16.2).
