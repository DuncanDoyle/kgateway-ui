1. **P1 — Missing and stale status can report healthy.** [plan:3687](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:3687) skips absent conditions and skips `True` before checking generation. Policies with absent or stale ancestors also produce no finding, while the check returns OK. This violates D-006 and Review Focus 4. Check freshness before status, distinguish missing required conditions from unsupported conditions, and test stale `True` plus absent status through the API.

2. **P1 — Watch failures disappear after initial sync.** [plan:1430](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:1430) clears errors whenever `HasSynced()` is true. In client-go v0.36.2, that records initial synchronization; it remains true after subsequent connection or authorization failures. Additionally, Namespace/Pod/Deployment errors are omitted from `Snapshot.Access`, and an error counts as “settled.” Stale or unavailable inputs can therefore appear readable. Track current collection availability separately from initial sync and propagate typed-informer failures.

3. **P1 — Recalculation makes old evidence appear fresh.** [plan:3476](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:3476), [plan:3807](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:3807): reports receive `Now`, but successful metrics have no age limit. Repeated computation can indefinitely reuse an old zero-reject result. Frontend staleness checks only the report timestamp, and stale Gateway rows retain their green badges. Carry and enforce freshness for each required signal across every health surface.

4. **P1 — Switching installs can display the previous install’s health and inventory.** [plan:6192](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:6192) enables `keepPreviousData` for install-specific requests. `InstallPage` accepts that data under the new URL and builds resource links using the new install ID. During loading, install B can display install A’s green result and resources. Clear data on identity changes or validate response identity before rendering.

5. **P1 — Parent status is scoped only by controller name.** [plan:3712](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:3712) evaluates every route parent carrying a matching controller name. With disjoint installs sharing that name, a route attached to Gateways in both scopes imports one install’s failures into the other. Old status for removed parentRefs also remains eligible. Match status to current parentRefs and the resolved parent’s install ownership.

6. **P1 — Reference groups are ignored during assignment.** [plan:2318](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:2318) resolves parents using kind and namespace/name, ignoring `group`; ListenerSets similarly share a namespace/name-only index. A foreign-group `Gateway` reference can resolve to an unrelated Gateway API object, producing wrong counts and ownership. Resolve using full group/kind/namespace/name identities.

8. **P1 — The frontend application lacks required ambient type declarations.** Task 12’s app tsconfig includes only `src` and `vite.config.ts`, while [plan:6839](/Users/ddoyle/Development/claude/kgateway-ui-claude/docs/phases/phase-1/implementation-plan.md:6839) imports an SVG without `vite/client` declarations.
