1. **P1 — The map walk does not recover from an old-format cursor’s 400.**  
   [mapData.ts:89](/Users/ddoyle/Development/claude/snellius-phase6/web/packages/shell/src/pages/map/mapData.ts:89).

   The decoder now requires four `R` elements, rejecting older two-element cursors. The ordinary Traffic list recovers through `useList`, dropping the cursor and loading page one. The map’s separate `fetchPages` has no catch around continuation requests: a 400 escapes before revision comparison can restart the walk. Its shared retry policy also suppresses retries for 400 ([hooks.ts:24](/Users/ddoyle/Development/claude/snellius-phase6/web/packages/shell/src/api/hooks.ts:24)).

   A server upgrade between pages therefore leaves a failed/stale map or first-load prefix instead of restarting automatically. Catch continuation-cursor rejection, restart within the bounded attempt loop, and cover this upgrade case.

2. **P2 — Revision omits rendered finding titles.**  
   [digest.go:155](/Users/ddoyle/Development/claude/snellius-phase6/pkg/paths/digest.go:155).

   Signal hashing includes kind, code, ref, state and listener, but excludes the finding message. The API subsequently adds that message as `title` ([paths.go:279](/Users/ddoyle/Development/claude/snellius-phase6/pkg/api/paths.go:279)), and the map renders it through `signalText`.

   For example, changing a rejected Backend’s condition reason from `Invalid` to `UnsupportedValue` can change the displayed explanation while preserving its finding code, resource and severity. Revision stays unchanged, so the walk can accept pages containing different rendered explanations as consistent. Include rendered titles in the visible-result digest and add a same-count, same-state explanation-change regression.
